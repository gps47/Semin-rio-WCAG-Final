01 — Introdução

Por que acessibilidade importa?

Acessibilidade web significa garantir que qualquer pessoa — independentemente de deficiências visuais, motoras, cognitivas ou auditivas — possa perceber, operar e compreender conteúdo digital. O WCAG, publicado pelo W3C, é o padrão internacional que guia esse trabalho.

👁️

Visual

Cegueira, baixa visão, daltonismo. Afeta como usuários percebem cores, textos e imagens.

🦻

Auditiva

Surdez ou perda parcial. Impacta consumo de vídeos, podcasts e alertas sonoros.

🖐️

Motora

Dificuldade de usar mouse ou teclado. Requer interfaces navegáveis por voz ou teclado.

🧠

Cognitiva

Dislexia, autismo, TDAH. Clareza, consistência e linguagem simples fazem diferença.

02 — Definição e Princípios

Os 4 princípios POUR

O WCAG organiza todas as suas diretrizes em quatro princípios fundamentais. Todo conteúdo web deve ser Perceptível, Operável, Compreensível e Robusto.

P

Perceptível

Informações e componentes de UI devem ser apresentados de forma que os usuários possam percebê-los — não apenas com a visão.

O

Operável

Componentes de interface e navegação devem ser operáveis por qualquer meio de entrada: teclado, voz, ponteiro.

U

Compreensível

Informação e operação da UI devem ser compreensíveis. Linguagem clara, erros descritivos, comportamento previsível.

R

Robusto

Conteúdo deve ser interpretado de forma confiável por tecnologias assistivas e diferentes agentes de usuário.

Níveis de conformidade WCAG

O padrão define três níveis de critérios de sucesso:

Nível Descrição Exemplos de critérios Obrigatório?
A Mínimo básico — sem ele o site é inacessível Texto alternativo, navegação por teclado, sem conteúdo piscante Sim (lei)
AA Padrão de mercado e exigência legal na maioria dos países Contraste 4.5:1, legendas em vídeos, foco visível, labels em formulários Recomendado
AAA Nível mais alto — nem sempre possível em todo conteúdo Contraste 7:1, linguagem de sinais, leitura em nível fundamental Ideal

05 — Mini Projeto

O que foi construído

Esta própria página é o projeto. Ela demonstra na prática os princípios WCAG 2.2 nível AA: semântica HTML, contraste, foco, ARIA e formulários acessíveis.

Problema / Objetivo

Criar uma página educacional interativa sobre WCAG que seja ela mesma acessível — provando que design atraente e acessibilidade não são excludentes.

Materiais e métodos

1

HTML semântico

Uso de <main>, <nav>, <section>, <article>, atributos lang e estrutura de headings lógica.

2

WAI-ARIA

Roles (tablist, tabpanel, alert), aria-label, aria-describedby, aria-selected, aria-hidden e aria-live.

3

Contraste e cores

Paleta validada com razão > 4.5:1 para texto normal e > 3:1 para componentes UI — aprovando nível AA.

4

Navegação por teclado

Foco visível em todos os elementos interativos, skip link, tabs operáveis com setas e Enter, sem armadilhas de foco.

5

Formulário acessível

Labels programaticamente associados, aria-describedby para hints, validação com mensagens de erro acessíveis.

Resultados alcançados

  • Página navegável totalmente por teclado.
  • Implementação de skip link para acesso rápido ao conteúdo principal.
  • Formulário com labels, validação acessível e feedback ao usuário.
  • Demonstrações práticas de contraste, foco e uso de ARIA.
  • Estrutura semântica compatível com leitores de tela.
  • Alternância de tema claro/escuro com contraste validado em ambos os modos.
  • Teclado virtual on-screen para apoio a usuários com limitações motoras.

Exemplo de código 1 — Skip Link (Pular Navegação)

O critério WCAG 2.4.1 exige um mecanismo para pular blocos de conteúdo repetidos (como o menu) e ir direto ao conteúdo principal. É o primeiro elemento focável da página. 

<!-- HTML: primeiro elemento dentro do <body> -->
<a href="#main-content" class="skip-link">
  Pular para o conteúdo principal
</a>

<main id="main-content">
  ...
</main>

/* CSS: escondido fora da tela até receber foco */
.skip-link {
  position: fixed;
  top: -100px;      /* fora da área visível */
  left: 1rem;
  background: #f5c842;
  color: #000;
  padding: .5rem 1.2rem;
  transition: top .2s;
}

.skip-link:focus {
  top: 0;           /* aparece ao pressionar Tab */
}

Exemplo de código 2 — Alternância de Tema Acessível

O botão de tema usa aria-pressed para informar o estado atual (pressionado ou não) e aria-label dinâmico, que descreve a ação ao invés do estado — prática recomendada para leitores de tela. 

<!-- HTML -->
<button id="theme-toggle"
        aria-label="Alternar para modo claro"
        aria-pressed="false">
  <span class="icon" aria-hidden="true">🌙</span>
  <span id="theme-label">Escuro</span>
</button>

/* CSS: transição suave entre temas */
body {
  transition: background .35s ease, color .35s ease;
}

// JavaScript
const html = document.documentElement;
const btn  = document.getElementById('theme-toggle');

btn.addEventListener('click', () => {
  const atual = html.getAttribute('data-theme');
  const novo  = atual === 'dark' ? 'light' : 'dark';

  html.setAttribute('data-theme', novo);
  localStorage.setItem('wcag-theme', novo);

  // Atualiza o estado para leitores de tela
  btn.setAttribute('aria-pressed', novo === 'light');
  btn.setAttribute('aria-label',
    novo === 'dark' ? 'Alternar para modo claro' : 'Alternar para modo escuro');
});

Exemplo de código 3 — Abas (Tabs) Acessíveis

As abas seguem o padrão WAI-ARIA Tabs Pattern: o HTML define a estrutura com role="tablist", role="tab" e role="tabpanel"; o JavaScript controla qual aba está ativa e permite navegação pelas setas ← / →, exatamente como o usuário descobriu nesta seção. 

<!-- HTML: estrutura com ARIA roles -->
<div role="tablist" aria-label="Exemplos">
  <button role="tab"
          aria-selected="true"
          aria-controls="painel-1"
          id="aba-1">Aba 1</button>

  <button role="tab"
          aria-selected="false"
          aria-controls="painel-2"
          id="aba-2">Aba 2</button>
</div>

<div role="tabpanel"
     id="painel-1"
     aria-labelledby="aba-1"
     aria-hidden="false">
  Conteúdo da aba 1...
</div>

<div role="tabpanel"
     id="painel-2"
     aria-labelledby="aba-2"
     aria-hidden="true">
  Conteúdo da aba 2...
</div>

// JavaScript: ativa abas e habilita navegação por setas
const abas    = document.querySelectorAll('[role="tab"]');
const paineis = document.querySelectorAll('[role="tabpanel"]');

function ativarAba(aba) {
  // 1. Desativa todas as abas e esconde todos os painéis
  abas.forEach(a => a.setAttribute('aria-selected', 'false'));
  paineis.forEach(p => p.setAttribute('aria-hidden', 'true'));

  // 2. Ativa a aba clicada e mostra o painel correspondente
  aba.setAttribute('aria-selected', 'true');
  const idPainel = aba.getAttribute('aria-controls');
  document.getElementById(idPainel).setAttribute('aria-hidden', 'false');
}

abas.forEach(aba => {
  // Clique do mouse
  aba.addEventListener('click', () => ativarAba(aba));

  // Navegação por teclado (padrão WAI-ARIA)
  aba.addEventListener('keydown', e => {
    const lista = [...abas];
    const indice = lista.indexOf(aba);

    if (e.key === 'ArrowRight') {
      const proxima = lista[(indice + 1) % lista.length];
      ativarAba(proxima);
      proxima.focus(); // move o foco junto com a seleção
    }

    if (e.key === 'ArrowLeft') {
      const anterior = lista[(indice - 1 + lista.length) % lista.length];
      ativarAba(anterior);
      anterior.focus();
    }
  });
});

06 — Conclusão

Resultados e aprendizados

Este projeto demonstrou que acessibilidade web não é limitação criativa — é uma disciplina de engenharia e design que, quando aplicada corretamente, melhora a experiência para todos os usuários.


Os principais resultados alcançados foram: página aprovada nas ferramentas Axe DevTools e Lighthouse Accessibility (>95 pontos), navegação 100% funcional via teclado, contraste conforme AA em todos os textos, formulário com feedback acessível em tempo real e estrutura semântica validada por leitores de tela (NVDA/VoiceOver).


Conclusão central: o WCAG não é burocracia — é o conjunto mínimo de respeito que desenvolvedores devem ao próximo bilhão de usuários que acessam a web com limitações. Implementar acessibilidade é mais barato no início do projeto do que corrigir depois.
